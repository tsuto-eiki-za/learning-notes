## Chapter 11 クライアントとサーバーのバンドル境界

`use client`や`use server`は、バンドル境界を宣言するためのもの

Next.js はサーバー側処理(Server)とクライアント側処理(Client)の二段階ある。

- **Server**：DB アクセス、fetch、秘密情報
- **Client**：ボタン、クリック、状態管理

この二つは別のバンドル(ServerBundle と ClientBundle)に分けられる

- **Server Bundle**

  - サーバーでしか動かない
  - DB、Server Actions、秘密キー OK

- **Client Bundle**

  - ブラウザに送られる
  - クリック、useState、イベント

`use client` / `use server`は 「どのバンドルに含めるか」を宣言するもの
実行環境を指定しているわけではない

### 2 つの世界、2 つのドア

`use client`や`use server`は、バンドル協会を宣言するためのもの
家で例えると

[ サーバーの家 ] ──🚪── [ クライアントの家 ]

この 🚪（ドア）が `"use client"` と `"use server"`

- `use client`  
  サーバーの世界から、クライアントの世界へ入るドア  
   サーバー側から、この部品を使えるようにする(サーバーへ Client Components を公開する)
- `use server`  
   クライアントの世界からサーバーの世界へ入るドア  
   クライアントへ Server Functions を公開する

<br>

#### Server Components

`use server`はクライアントから呼べるサーバー関数を作るためのもの

```tsx
"use server";

export async function updateProfile() {
  // DB 更新など
}
```

> **Server Components には `use server` が必要？**
>
> Next.js はデフォルトでサーバーコンポーネントだから不要！！

#### Client Components

`use client`はこのファイルはブラウザに送る JS ですよという宣言

```tsx
"use client";

export function Button() {
  return <button>Click</button>;
}
```

### import できるものできないもの

#### :x: Client → Server を直接 import はできない

```tsx
// ❌ NG
"use client";
import { getUser } from "./server-only";
```

ブラウザにサーバー専用コードを送れない

Server → Client はできる

```tsx
// Server Component
import Button from "./button"; // "use client"
```

サーバーは「部品」として k 流アイアント用 JS を扱える

#### `server-only`

```tsx
import "server-only";
```

「このファイルは Server Bundle 専用です」  
「Client Bundle から使われたらビルドエラーにして」

と宣言するもの。  
クライアントコンポーネントで import されている場合ビルド中にえらーになる

## Chapter12 Client Components のユースケース

Client Components で使うべき代表的な 3 つのユースケース

### クライアントサイド処理

最もわかりやすい使い方。

以下のような場合

- `onClick()` や `onChange()` といったイベントハンドラの利用
- 状態 hooks(`useState()`や `useReducer()`)やライフサイクル hooks(`useEffect()`など)の利用
- ブラウザ API の利用

例

```tsx
"use client";

import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>You clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>Click me</button>
    </div>
  );
}
```

### サードパーティコンポーネント

サードパーティライブラリが RSC に未対応な場合は、利用者側で Client Boundary を明示しなければいけない。

> **Client Boundary**
>
> `"use client"`を書いて Client Bundle 側であることを宣言する

この場合のやり方は以下の 2 つ

`"use client"`を指定して re-export する

```tsx
"use client";

import { Accordion } from "third-party-library";

export default Accordion;
```

<br>

利用者側で`"use client`を指定する

```tsx
"use client";

import { Accordion } from "third-party-library";

export function SideBar() {
  return (
    <div>
      <Accordion>{/* ... */}</Accordion>
    </div>
  );
}
```

### RSC Payload 転送量の削減

3 つ目は、RSC Payload の転送量を減らしたい時。  
Client Components はクライアントサイドで実行される  
→ **Client Components が多いほど JavaScript バンドルサイズは増加する。**

Server Components は RSC Payload として転送される  
→ **Server Components がレンダリングする React Element や属性が多いほど転送量が多くなる。**

つまり、
Client Components を減らして Server Components を増やしすぎると RSC Payload がめっちゃ増えるので、、、  
Client Components の JavaScript 転送量と Server Components の RSC Payload 転送量はトレードオフといえる

> **ペイロード**
>
> ネットワークで送られるデータ量

> **RSC Payload**
>
> ServerComponents のレンダリング結果をクライアントに送るためのデータ  
> サーバー側で作られる`<div>...<div>`のような構造データ

> **トレードオフ**
>
> A をよくすると B が悪くなる関係

Client Components を含む JavaScript バンドルは 1 回しかロードされないが、
Sever Components はレンダリングされるたびに RSC Payload が転送される。

つまり、、

Server Component だけの場合

```tsx
export async function Product() {
  const product = await fetchProduct();

  return (
    <div class="... /* 大量のtailwindクラス */">
      <div class="... /* 大量のtailwindクラス */">
        <div class="... /* 大量のtailwindクラス */">
          <div class="... /* 大量のtailwindクラス */">
            {/* `product`参照 */}
          </div>
        </div>
      </div>
    </div>
  );
}
```

上記の Server Component において

ページ遷移のたびに以下のことが起きる

- サーバーで JSX を組み立てる
- JSX の構造（大量の div 情報）を送る
- クライアントで表示

→ アクセスのたびに毎回、でかい情報量が送られる

以下のコードのように Server Componets ではデータフェッチのみを行い、
ReactElement 部分は Client Components に分離することで RSC Payload の転送量を削減することができる

```tsx
export async function Product() {
  const product = await fetchProduct();

  return <ProductPresentaional product={product} />;
}
```

```tsx
"use client";

export function ProductPresentaional({ product }: { product: Product }) {
  return (
    <div class="... /* 大量のtailwindクラス */">
      <div class="... /* 大量のtailwindクラス */">
        <div class="... /* 大量のtailwindクラス */">
          <div class="... /* 大量のtailwindクラス */">
            {/* `product`参照 */}
          </div>
        </div>
      </div>
    </div>
  );
}
```

## Chapter 13 Composition パターン

RSC を活かすためには Server Components 中心の設計が重要。そのため、Client Components を適切に分離・独立させる。  
Client Components を独立した形に切り分ける方法は以下の２つ

### コンポーネントツリーの末端を Client Components にする

シンプルに Client Boundary を下層に限定する。

例  
検索バーを持つヘッダーの場合、ヘッダー全体ではなく検索バーの部分を Client Boundary とし、ヘッダー自体は ServerComponennts に保つ

```tsx
import { SearchBar } from "./search-bar"; // Client Components

// page.tsxなどのServer Componentsから利用される
export function Header() {
  return (
    <header>
      <h1>My App</h1>
      <SearchBar />
    </header>
  );
}
```

### Composition パターンを活用する

上記の方法はシンプルで簡単だけど、どうしても上位のコンポーネントを Client Components にする必要がある時もある。そんな時は**Composition パターン**を使う。
Composition パターンとは、ざっくりいうと  
Client Component が Server Component を**import せずに包む**方法

#### **Children**

「コンポーネントのタグで囲まれた中身専用」の props

children を使うコンポーネントの例

```tsx
function Box({ children }: { children: React.ReactNode }) {
  return <div className="box">{children}</div>;
}
```

使う側 ↓

```tsx
<Box>
  <p>こんにちは</p>
  <button>押す</button>
</Box>
```

この時、React は裏でこのような感じ

```tsx
<Box
  children={
    <>
      <p>こんにちは</p>
      <button>押す</button>
    </>
  }
/>
```

composition を使った例

```tsx
"use client";

import { useState } from "react";

// `children`に`<UserInfo>`などのServer Componentsを渡すことが可能！
export function SideMenu({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);

  return (
    <>
      {children}
      <div>
        <button type="button" onClick={() => setOpen((prev) => !prev)}>
          toggle
        </button>
        <div>...</div>
      </div>
    </>
  );
}
```

<br>

```tsx
import { UserInfo } from "./user-info"; // Server Components
import { SideMenu } from "./side-menu"; // Client Components

/**
 * Client Components(`<SideMenu>`)の子要素として
 * Server Components(`<UserInfo>`)を渡せる
 */
export function Page() {
  return (
    <div>
      <SideMenu>
        <UserInfo />
      </SideMenu>
      <main>{/* ... */}</main>
    </div>
  );
}
```

## Chapter 14 UI をツリーに分解する

React の基本的な設計思想は、UI をコンポーネントのツリーで設計すること。  
ページやレイアウトなどの実装は UI をツリーに分解することから始める。  
これにより、データフェッチコロケーションや Composition パターンの早期適用を目指す。

> データフェッチコロケーションや Composition パターンは、後から適用しようとすると大きな手戻りを生むかもなので、早期から考慮して設計するのが望ましい。

### 「大きなコンポーネント」と「小さなコンポーネント」

React は UI をコンポーネントとして表現する。ページなどの UI は「大きなコンポーネント」であり、これらは「小さなコンポーネント」を組み合わせて実装する。  
「大きなコンポーネント」→「小さなコンポーネント」のようにトップダウンで設計することが望ましい。

### 実装手順

以下のように進める。

1. **設計: UI をツリーに分解する**
2. **仮実装: コンポーネントのツリーを仮実装**
3. **実装: 各コンポーネントの詳細実装**
   - Server Components を実装
   - Shared/Client Components を実装

<br>

具体的な実装例は本文を見る  
https://zenn.dev/akfm/books/nextjs-basic-principle/viewer/part_2_container_1st_design#fn-74a3-2

## Chapter 15 Container/Presentational パターン

コンポーネントのテストで採用されがちな React Testing Library や Storybook の RSC 対応状況が芳しくない、、、

→ テストをしたい Server Components は「テストしにくいデータフェッチ部分」と「テストしやすい HTML 部分」を分離しておく！！

- **Container Components**: データフェッチなどのサーバーサイド処理を担当
- **Presentational Components**: データフェッチを含まない Shared Components や Client Components を担当
